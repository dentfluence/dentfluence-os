The one thing to understand first

The engine is built. The switches are off.

Dentfluence has a genuinely strong backbone — an ActivityEngine / RulesEngine event spine, a CommunicationEngine + Guard, a Workflow and Automation engine, TaskEngine, RelationshipEngine, IdentityResolver and more. The internal review calls this backbone "fail-safe and well-designed." But most of it is gated behind feature flags that are still OFF, so the app largely runs on older legacy paths while the new engines run in shadow or lie dormant.

Your risk isn't missing code — it's untested cutovers and the gap between "exists" and "wired live."

Backend wiring & connections — how the pieces talk

The bus exists; the gap is producers that emit into it.

The event spine

ActivityEngine + RulesEngine + the ActivityRecorded event already are the internal event bus. Flow is producer → event → rules → action. The real gap is missing producer calls — the bus works, but not every module emits into it yet. The hardening sprint wired 4 previously-dead rules that had no producers.

Communication path

  • CommunicationEngine sends wrapped by CommunicationGuard (consent + factors)
  • guard.consent_required ON in prod
  • End-state comm.single_gateway is OFF → multiple send paths still exist

PRE is the sole front door

  • Never GET-link into routes/communication.php from anywhere
  • Forms POSTing to communication.* are fine

Relationship identity

  • One Relationship per patient, always (findOrCreateForPatient())
  • New patients auto-linked; history needs relationship:backfill --apply --force

Marketing

  • Provider pattern: Standalone/manual vs Integrated
  • Meta/Google connect PARKED (biz registration + approvals); WordPress works
  • Graph API pinned to v23

Modules & the SaaS control plane

  • Modules (app/Modules/): Appointment, Hq, Huddle, Lab, Patient, PracticeProtocols, Treatment — loosely coupled, each designed to become a standalone/premium product
  • HQ / SaaS layer: clinics, plans, subscriptions, tickets tables + is_superadmin exist (2026-07-16). Schema present — isolation NOT yet enforced.

VPS vs Local drift — what's live vs only on your PC

The VPS only changes when you run deploy.sh. Git is fully synced; the drift is elsewhere.

Deploy model

bash deploy.sh in /opt/dentfluence → git pull --ff-only from main → rebuild Docker → migrate --force → cache config/views. route:cache intentionally skipped (closure redirects). No PHP on the host — all in the app container. Always check docker compose ps after every deploy (queue worker has crash-looped before).

Git state

Local main == origin/main (0 ahead / 0 behind). Every committed feature is pushed and deployable.

The actual drift — two kinds

1 · Uncommitted local work

The WhatsApp Click-to-Chat engine + blog editor tweaks + marketing calendar/subtabs — edits across ~16 files. Not on GitHub, not on the VPS. Exists only on your PC.

2 · Pushed but maybe not deployed

Several items are flagged "NEEDS bash deploy.sh" (Carbon 500 fix, prescription weight field). Anything committed after the last deploy is live on GitHub but not yet on the VPS. Cannot be verified from here — SSH in and check the deployed commit hash against 703393a.

⚠️ Two live-data facts

The 1,810-item recall backlog and the 17 orphan relationship rows are in the production DB — real cleanup, not local test noise. And the next deploy after recent commits carries real schema changes (migrate --force auto-applies them) — review before deploying.

Commercial summary — for anyone outside the build

Dentfluence is a Laravel-based Dental Clinic Operating System, well past MVP for a single clinic. The bones are strong: a transactional, audit-trailed finance chain; a disciplined API layer (Sanctum + shared services) that already powers a companion Flutter mobile app; a consent-aware communication engine (DPDP-oriented); and a modular architecture where each module (PRE, Marketing, Inventory, Lab, Membership, Case Acceptance, Blog Hub) is designed to stand alone as a premium/subscription product.

Shippable today: a full clinic operating loop — patients, appointments, consultations, treatment planning, prescriptions, billing/finance, inventory, lab, and a patient-relationship + recall engine. Enough to run a real single clinic end-to-end, and much of it is deployed on the Hostinger VPS.

Where it's heading (built, staged behind flags): a unified communication gateway, an automation/workflow engine, a Case Acceptance patient-microsite experience, a Blog Marketing Hub, and multi-clinic SaaS (HQ control plane with plans/subscriptions/tickets). The sophistication is already coded — the roadmap is largely about validating and switching it on, not building from scratch.

Honest maturity line

Production-ready for clinic #1 after the critical-fix list is tested (~1–2 weeks of focused QA). Not yet safe for clinic #2 until multi-tenant clinic_id isolation and PHI encryption land — that's the gating work between "one clinic" and "SaaS."
