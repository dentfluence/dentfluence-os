# Patient Journey V1.1 — Engineering Architecture Proposal

**Date:** 2026-07-25 · **Status:** PROPOSAL — nothing implemented. For CEO challenge → freeze → slice-by-slice approval.
**Evidence base:** the four completed forensic audits (`patients-v1_1-clinical-care-audit.md`, `patient-journey-audit.md`, `pre-relationship-engine-audit.md`, `legacy-prm-audit.md`). Schema facts re-verified against migrations during drafting (communication_queue and comm_activity_logs column lists confirmed).

**Design stance, stated up front:** the audits show Dentfluence does not need a new relationship system — it needs the one that already exists to be *finished*. `communication_queue` is already the de-facto spine (11 writers). `comm_activity_logs` is already the attempt ledger (written daily, with actor + meta). `OutcomeAutomationService` is already the outcome engine (on one surface). `TodayActionsProjector` is already the read model (switched off). `TreatmentPlanAcceptanceService` is already the decision door (for one of four decisions). This proposal is ~70% "connect and finish", ~30% "build new". Every recommendation below is in-place, additive, and reversible by flag.

## PART B — What I would build new (and why nothing existing can do it)

1. **`plan_decisions` table + decision methods on the acceptance service** (Patients-owned). Append-only: `treatment_plan_id, decision(presented|accepted|rejected|deferred), decided_at, recorded_by, reason, defer_until, source(surface), created_at`. Why new: decisions must be *historical facts with authorship*; today they are one nullable timestamp (`accepted_at`), one overloaded status ('cancelled'), and one read-time heuristic. No existing store can hold "rejected on 24 Jul by Dr. X because cost, deferred until Sept" without destroying the previous fact. `accepted_at`/`status` remain as derived/compat mirrors — nothing existing breaks.
2. **`RelationshipWorkService`** — the single write door for the spine (open obligation, record activity, apply outcome, claim/release, reconcile). Why new: 11 uncoordinated writers is the audited disease; the codebase's own proven cure is a one-door service (`TreatmentVisitService`, `TreatmentPlanAcceptanceService`, `PatientService::register`). This is a service, not a table.
3. **Seven nullable columns on `communication_queue`** (verified absent from all migrations): `assigned_to_id` FK users (the existing `assigned_to` is a display name string), `claimed_by` + `claimed_at` (concurrency, Part 13), `next_action_at` datetime (precise "retry 4:00 PM"; today only `follow_up_date` date + `follow_up_time` string, frozen at creation), `source_type` + `source_id` (polymorphic reference to the fact that spawned the obligation — treatment_plan, appointment, lead; `lab_case_id` already exists and stays), `branch_id` (verified absent — the Huddle branch-leak root cause). Why: ownership, concurrency, the "why does this call exist" link, and tenancy cannot be expressed in existing columns.
4. **Two detectors** (console commands in the existing RecallEngine style): `TreatmentRecoveryDetector` (plans with started-but-incomplete items + no future appointment → obligation purpose `treatment_recovery`) and `DecisionFollowupDetector` (presented plans with no decision after N days → purpose `decision_followup`; replaces the dead `approved_plan_no_appt`). Why: nothing detects the two highest-value leaks; both are *derived* from canonical facts per CEO Part 15 — no status columns added.
5. **Two appointment events + one reconciliation listener**: `appointment.booked` and `appointment.attended` emitted from `AppointmentService` through the existing ActivityEngine spine; a `ReconcileRelationshipWork` listener that closes/annotates matching open obligations (outcome `appointment_booked`, link stored). Why: the audited #1 loop-closure gap; no existing code path connects booking back to the work that prompted it (verified: zero comm_queue references in AppointmentService).
6. **Doctor waiting queue + Start Consultation handoff** (Appointments-owned screen; Patients-owned creation): a view over `appointments where status='checkin'` grouped by doctor, with a Start Consultation button → existing `consultations.create` route carrying `appointment_id` → store() sets appointment_id/doctor_id/branch (check-in explicitly does NOT create the consultation). Why: today check-in dead-ends and `appointment_id` is a cosmetic dropdown; this is a small screen + a route parameter, not new architecture.
7. **Action Board v2** (evolution of `relationship/today`): three lanes (DUE / ATTEMPTED–NEXT / DONE TODAY), one card per patient, context block, claim indicator, honest counts ("50 of 1,810"). Why: UI work on top of the projector; no existing screen collapses per-patient or shows lanes.
8. **`ContextAssembler`** (read-only service): given an obligation, composes the Part-5 "why" — source fact, journey stage, last attempts from `comm_activity_logs`, previous outcome, today's objective — for the drawer now and V1.2 AI later. Why: context must be *derived live from facts*, not snapshotted into columns; no existing service composes cross-module context (the profile services come closest but are patient-page-shaped).
9. **`last_visit_date` writers + backfill command** (no new column — semantics + writers for the existing dead column; Part F/§17 defines the semantics first). Why: the recall engine's only input currently has no producer.
10. **A handful of API endpoints** under `/api/v1/relationship-work/*` mapping 1:1 to `RelationshipWorkService` — mostly refactors of existing Api/V1 relationship endpoints onto the service rather than genuinely new surface.

Explicitly NOT building: a journey-state machine table (stage is derived from facts; the existing dormant `relationship_journeys` states stay dormant), a new activity table, a new work table, AI scripts, call-log capture (adapter contract only, Part H), shift-roster modeling.

## PART F — Data migration plan (zero destructive reset)

Ground rules for every step: additive schema only; every backfill is a console command with `--dry-run` default producing a reconciliation report (the `SyncCallOutcomeClosesTask` pattern); DB snapshot before each production backfill; nothing is deleted or overwritten — supersession is expressed as `status='closed'` + `outcome='migrated'` + meta pointing to the successor; rollback = feature flag off + (for backfills) reversal scripts driven by the migration tags themselves.

|---|---|---|---|---|---|---|
| `leads` | preserved verbatim | nothing (no schema change) | everything | manual-add phone dedup is a *future* PRE improvement, not a migration | `lead_activities` untouched | n/a |
| `follow_ups` | preserved; open rows become spine obligations (purpose `follow_up`, source_type=follow_up, source_id=row id); originals marked completed with outcome `migrated` | open `pending` rows only | completed/history rows | match on (patient/lead + open) against existing spine rows before insert; collision → link, don't duplicate | original rows never deleted; obligation meta carries origin | report: open follow_ups vs created obligations vs collisions, per patient; reversal: delete obligations WHERE meta.origin='follow_ups_backfill', reopen originals |

**Pre-cutover reconciliation reports (the gate for every production step):** open-work census per store before/after (counts by purpose/status/branch); per-patient open-obligation diff (no patient may lose visibility of unresolved work — the invariant is *count of patients with ≥1 visible open item* never decreases un-explained); orphan report (obligations whose source facts don't resolve); assignee-mapping report; recall eligibility diff (old query vs new semantics — expected to *shrink*); `comm_activity_logs` and `activities` row-count invariance.

## PART G — Web + Mobile: one workflow

**The contract layer is the service layer.** Both surfaces converge on the same four classes: `RelationshipWorkService` (open/claim/record/apply-outcome/release), `OutcomeAutomationService` (the only next-action generator), `CommActivityLog` (the only attempt ledger), `TodayActionsProjector` reads (the only board feed). Web controllers (`TodayController`, board endpoints) and `Api/V1` endpoints become thin adapters over identical calls — the codebase's own proven pattern (`TreatmentVisitService` is called by both surfaces today with zero drift).

**Divergences that must be deleted** (all audited): web `logAction` bypassing the outcome engine; mobile `logAction` ignoring `closes_task`; 'will call back' closing on web vs rescheduling on mobile; mobile-only `attempt_count` incrementing; `waiting_for_patient` rows vanishing from the board; `HuddleBoardApiService::subDay()` vs `ClinicFlowRange`; mobile outcome sheet vocabulary vs web option lists (one `ActionOptionList`-driven vocabulary served to both).

**Contracts both consume:** `GET board` (lanes, per-patient cards, honest counts), `GET obligation/{id}/context` (ContextAssembler output), `POST obligation/{id}/claim|release`, `POST obligation/{id}/outcome` (option key + note [+ appointment payload]), `POST activity` (manual entry, Part H). Parity is pinned by contract tests asserting web route and API route produce identical state transitions for every outcome key — the missing test class the parity audits kept flagging.

**Remote work (Part 7) falls out for free:** PRE is already browser+mobile; once the board carries why/history/owner/next-action and outcomes route through one engine, a staff member at home has everything reception has. The only remote-specific work: the permission hardening (auth-only relationship routes are unacceptable for WFH exposure) and consent gating on sends (already enforced in `WhatsAppLinkService`).

## PART H — Manual entry + call-log adapter: one architecture

**Manual entry is the primary interface, not a fallback bolted on.** `RelationshipWorkService::recordActivity(subject, type[out-call|in-call|missed-call|whatsapp|in-person|other], outcome_key, note, next_action?)` — writes `comm_activity_logs` (actor, surface='manual', meta), applies the outcome through the same engine, and creates an obligation if the interaction implies one and none is open. The existing drawer Log, "+ Add Communication" form, and `PatientCommunicationController` all become thin fronts on this one method (the latter keeps writing `patient_communications` for timeline compat until consolidated).

**Call log = the same method with a different source.** The optional Android adapter (V1.2+) posts raw call events to a staging state — untagged rows (reusing the queue with `purpose='untagged_call'`, `source_engine='call_log'`, no patient) surfacing in a small "Tag inbox" lane. Human tags (Old Patient/New Patient/New Lead/Ongoing/Vendor/Lab/Doctor/Spam/Other) → the tag handler calls the *same* `recordActivity`/lead-creation paths: identity is human truth, linking/attempt-counting/board updates are automated. V1.1 builds none of this — it only keeps the door open: `recordActivity` accepts `source` + `external_ref` in meta, and the queue's original `classification` column (verified in the base migration — the 2026-06-04 schema was literally designed for this) already models the tag vocabulary. No silo: a tagged call is indistinguishable downstream from a manual entry.

## PART I — Strict activity history

**Two-ledger model, both existing, both append-only:** `comm_activity_logs` = relationship attempt/outcome ledger (who called, when, outcome, note, next action — keyed to obligations); `activities` (ActivityEngine) = journey fact ledger (consultation done, plan presented/decided, appointment events). No third store. `comm_activity_logs` is sufficient with zero schema change — `meta` JSON carries surface, outcome_key, next_action, external_ref, correction pointers; `user_id`/`user_name`/`logged_at` already exist. (If query performance later demands promoted columns, that's an additive index migration, not a redesign.)

**Deletion prevention:** neither model gains delete routes; model-level guard (`booted()` deleting-throw except via an explicit `void()` path); role permissions exclude destroy; production DB user needs no DELETE on these tables long-term (ops hardening, post-V1.1). **Corrections:** append a `correction` row referencing the original (`meta.voids_id`); readers render the original struck-through with the correction — the original fact survives. **Legacy history:** migrated follow_up/task origins recorded in obligation meta; `lead_activities` stays as-is (timeline already reads it); nothing rewritten. **Timeline consumption:** one new `UnifiedTimelineService` adapter (`addRelationshipWork`) rendering attempt history + obligation open/close events, permission-filtered like every other source — additive, aggregator untouched. **AI (V1.2):** reads exclusively through `ContextAssembler` — a read-only, permission-aware composition of the two ledgers + clinical facts; AI never queries tables directly and never writes history.

## PART J — Staff cutover plan

0. **Hygiene gate:** commit all uncommitted work; smoke suite green (rollback + commit modes); prod `feature_flags` inventory (which recall path is actually live).
1. **Invisible foundations:** permission hardening, clinical decision + progress truth, `last_visit_date` semantics doc + writers (backfill dry-run only), dead-category fixes, spine columns. Staff see: nothing new, three board cards that finally work.
2. **One engine, same screens:** web outcomes routed through OutcomeAutomationService; attempt history in the existing drawer; existing screens keep working unchanged on top (they already read the same models — the compatibility layer is mostly free).
3. **Board v2 behind a flag, pilot of 1–2 staff** (e.g., the two receptionists in the CEO's own examples) working real recalls; daily reconciliation report; old board one click away.
4. **Backfills + queue reconciliation** with CEO-approved reports (Part F); recall emission switched to new semantics.
5. **Board v2 primary for all staff;** legacy surfaces (Follow-up Engine, Communication Recall, Missed Calls) demoted to linked read-only "archive" views; legacy schedulers replaced/disabled.
6. **Observation window** (2–4 weeks): parity counters, complaint-driven fixes, no retirements.
7. **Retirement slice** per Part E + final forensic re-audit + freeze.

Challenge to the CEO's sequence: I moved "compatibility with old screens" *before* the new board (stages 1–2) — because the audits show old screens already read the spine models, compatibility is the default state, and unifying the engine first means the pilot board demonstrates *better data*, not just better UI. Staff shock is lower when the first visible change is "the board finally shows why and history", not a new layout with old data quality.

## PART K — Failure / risk analysis

| Missed follow-ups | outcome routing bug drops the next action | service-enforced invariant (every outcome → resolved XOR next_action_at) + contract tests per outcome key; category-health signal |
| Lost history | migration rewrites/deletes ledger rows | ledgers are constitutionally untouched; row-count invariance check in every slice's verification; DB snapshots |
| Web/mobile drift re-emerges | a fix lands on one surface | single service layer + parity contract tests in CI; mobile changes require the same service call |

## PART M — Final engineering verdict

1. **Compatible?** Yes — unusually so. The audits show this architecture half-exists: the spine, ledger, outcome engine, projector, decision door, and event bus are all built. V1.1 finishes and connects them.
2. **Reuse vs new:** ~70–75% reuse/extend. Genuinely new: one table (`plan_decisions`), seven columns, two services (`RelationshipWorkService`, `ContextAssembler`), two detectors, two events + one listener, one screen evolution + one small queue screen.
3. **Biggest architectural change:** behavioral, not structural — all relationship work produced into and consumed from one spine through one service and one outcome engine. It's a consolidation of write paths, the exact move that already saved Patients (register()) and Visits (TreatmentVisitService).
4. **Highest-risk migration:** the attendance-semantics backfill + queue reconciliation (S3/S7) — it changes what 1,810 live rows mean and what tomorrow's board shows a working clinic. Hence: report gates, sampling, reversal commands, paused emission.
5. **Canonical spine:** `communication_queue`.
6. **Evolve, wrap, or replace?** Evolve *and* wrap: evolve the table (7 additive columns — it already has purpose, attempts, outcomes, SLA, dismissal audit, and its base migration's `classification` column shows it was designed for exactly this job), wrap all writes in `RelationshipWorkService`. Replacing means migrating live prod rows to gain nothing the columns don't provide; wrapping without evolving leaves name-string ownership and frozen dates. Code evidence is unambiguous: 11 writers and 6 read surfaces already treat it as the spine.
7. **Preserve all VPS data?** Yes. Every schema change is additive; every state change is tagged, reported, logged, and reversible; the two ledgers are constitutionally untouched; row-count invariance is a per-slice verification gate.
8. **Web+mobile one workflow without rewrite?** Yes — the divergence is at the controller layer, not the data layer. `TreatmentVisitService` proves both surfaces can share one brain in this codebase today. It's routing, not rewriting.
9. **Overengineered in the directive:** the full 10-state recall vocabulary as *stored* states (most are derivable from obligation status + `next_action_at` + outcome — store less, derive more); team/shift queue modeling (start with owner + claim; shifts are a human roster, not a schema); call-log adapter beyond the contract (correctly deferred by the directive itself); treating DONE-today as new machinery (the `includeDone` faded-card behavior already exists — polish it).
10. **What I'd simplify:** obligation purposes capped at a working set (~8: enquiry, decision_followup, treatment_recovery, post_op, recall, payment, lab_ready, manual) — every new purpose needs a justification, or the board becomes the 13-category engine again; one outcome vocabulary (option lists) instead of separate web/mobile/recall/lead sets; no stored journey stage anywhere.
11. **Missed requirement:** an **operational health surface** — the silent-dead-category disaster must be unrepeatable: every projector category, detector, and scheduler reports last-run/last-error somewhere an admin sees (a small admin panel + the existing log pattern). Secondary: KPI payoff (case-acceptance %, recall conversion, recovery rate) becomes nearly free once decisions and outcomes are facts — plan it for V1.15/V1.2 so the truth model visibly earns money; and backup/restore drill before S7.
12. **What I would refuse to change in the first release:** patient registration/merge (frozen); `TreatmentVisitService`'s clinical flow and billing handoff; any billing/invoice behavior; historical `communication_queue` row semantics (map forward, never rewrite meaning); the ledgers; and I would refuse any big-bang screen removal — old surfaces die only after staff have proven the new one, never on deployment day.
